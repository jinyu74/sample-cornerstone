# 공통 개발 절차 (Codex · Claude Opus)

이 문서는 이 저장소에서 일하는 모든 에이전트와 사용자가 따르는 공통 절차다. `AGENTS.md`(Codex)와 `CLAUDE.md`(Claude Opus)가 이 문서를 참조한다. 도구·구조·테스트·디자인 규칙은 [`AGENTS.md`](../AGENTS.md)를 그대로 따르고, 이 문서는 그 규칙을 이슈 → 브랜치 → PR → 병합 흐름에 연결한다. 두 문서가 충돌하면 더 엄격한 쪽을 따르고 Codex가 사용자에게 알린다.

## 1. 역할

| 주체         | 책임                                                                                                                                                                                                                    | 하지 않는 일                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 사용자       | 이슈 목적 확정, 중요 결정, PR 검토, `main` 직접 병합 또는 특정 PR·head에 대한 명시적 병합 요청                                                                                                                          | —                                                                                   |
| 감독 Codex   | 감독, 이슈·작업 지시서 작성, 작업 브랜치 생성, PR 오픈 전 사전 검수(코드 읽기와 검사 직접 실행), git commit·push, PR 생성·갱신, 리뷰어 생성, 리뷰 결과 PR 댓글 게시, 병합 요청 기록, 사용자가 병합을 요청한 head의 병합 | 사용자 병합 요청 없는 병합, 리뷰 결과나 일반 동의를 병합 허가로 보는 일, auto-merge |
| Codex 리뷰어 | PR 오픈 후 별도 Herdr 패널에서 `review-agent` 스킬로 전체 merge diff 읽기 전용 독립 리뷰, 결과를 감독 Codex에 보고, 지적을 감독 Codex·Claude에 전달                                                                     | 파일 수정, 커밋, 푸시, 리뷰 댓글 게시, 병합                                         |
| Claude Opus  | 작업 지시서에 따른 구현: 시나리오·인수 조건 정리, Red → Green → Refactor, 회귀·품질 검사 실행, 결과 보고, 감독 Codex·리뷰어 지적 수정                                                                                   | git commit·push, PR 생성·병합, Approve review, 브랜치 전환, 원격 설정 변경          |

- Claude는 파일만 수정하고 보고한다. git 이력과 원격 저장소를 바꾸는 작업은 감독 Codex만 한다.
- 에이전트는 로그인·권한 확인 질문에 사용자 대신 응답하지 않고, 사용자가 작성 중인 초안(입력창, 이슈·PR 초안, 사용자 편집 파일)을 수정하지 않는다.

## 2. 전체 흐름

1. **이슈:** 목적, 범위, 인수 조건과 검증 시나리오(정상·경계·실패), 제외 범위를 [이슈 템플릿](../.github/ISSUE_TEMPLATE/task.md)으로 적는다.
2. **작업 브랜치:** Codex가 `origin/main`을 최신으로 받은 뒤 그 위에서 브랜치를 만든다. 이름은 `<유형>/<이슈번호>-<짧은-설명>`이다(예: `docs/1-agent-pr-workflow`, `feat/12-calibration-editor`). 유형은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore` 중 하나다.
3. **작업 지시:** Codex가 [작업 지시서](#3-작업-지시서-codex--claude)를 Claude에 전달한다.
4. **구현 전 보고:** Claude가 담당 범위와 정상·경계·실패 검증 계획을 먼저 보고한다. 일상 범위는 보고 후 바로 진행한다.
5. **시나리오·인수 조건 → Red:** 실패 테스트를 작성하고 의도한 이유로 실패하는지 확인한다.
6. **최소 Green → Refactor:** 최소 구현으로 통과시킨 뒤 정리하고 다시 검증한다.
7. **회귀·품질 검사:** [변경 유형별 검증](#4-변경-유형별-검증)의 필수 검사를 실행한다.
8. **결과 보고:** Claude가 [결과 보고 형식](#5-결과-보고-형식-claude--codex)으로 Codex에 보고한다.
9. **사전 검수:** 감독 Codex가 PR 오픈 전에 diff를 읽고 필요한 검사를 직접 실행한다([6절](#6-codex-사전-검수-pr-오픈-전)). 발견 사항은 Claude에 수정 지시하고 4~8을 반복한다.
10. **PR:** 사전 검수가 끝나면 감독 Codex가 커밋·푸시하고 [PR 템플릿](../.github/pull_request_template.md)으로 review-ready PR을 연다.
11. **리뷰:** 감독 Codex가 별도 Herdr 패널에 Codex 리뷰어를 만든다. 리뷰어는 전체 merge diff를 독립 리뷰하고, 결함이 있으면 지적을 전달한다. 수정으로 head가 바뀌면 새 head를 다시 리뷰한다. 감독 Codex가 리뷰 결과를 PR 댓글로 게시한다. 이 댓글은 정식 Approve review가 아니다([7절](#7-pr-리뷰와-병합-허가)).
12. **병합 허가:** 사용자가 직접 병합하거나, 해당 PR·head에 대해 명시적으로 병합을 요청한다.
13. **병합:** 사용자가 병합을 요청한 경우에만 감독 Codex가 [병합 조건](#병합-조건)을 확인하고 그 head를 `main`에 병합한다.

- PR을 열기 전까지 필요한 구현과 수정은 사용자에게 다시 묻지 않고 끝낸다. 사용자에게는 완성된 review-ready PR을 보인다.
- 중요 결정이 필요한 부분만 질문하고 그 결정에 의존하는 작업만 기다린다([8절](#8-결정-기준)). 나머지 작업은 계속한다.

## 3. 작업 지시서 (Codex → Claude)

```markdown
- 이슈: #번호 (URL) / 브랜치: <브랜치> (main 기준 SHA)
- 목표: 한두 문장
- 담당 범위: 수정할 파일·계층·슬라이스
- 제외 범위: 다루지 않을 것
- 인수 조건: 확인 가능한 문장 목록
- 검증 시나리오: 정상 / 경계 / 실패
- 필수 검사: 4절 표에서 고른 명령
- 결정이 필요한 항목: 있으면 권장안·대안·영향과 대기 범위
- 결과 보고 위치: 파일 경로(필요할 때)
```

## 4. 변경 유형별 검증

모든 유형에서 실행하지 못한 검사는 통과로 적지 않고 미실행 사유를 남긴다. 이 표는 `AGENTS.md`의 품질 규칙(테스트·타입·lint·format·프로덕션 빌드·Storybook 빌드·관련 브라우저 검증)을 줄이지 않는다.

| 유형                  | 테스트 우선 방식                                                                                                                                                   | 필수 검사                                                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기능·버그 수정        | 정상·경계·실패 시나리오 → 의도한 Red(실패 명령과 이유 기록) → 최소 Green → Refactor. 버그는 재현 테스트를 먼저 만든다. 기대값을 약화하거나 테스트를 지우지 않는다. | `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm test:stories`, `pnpm build`, `pnpm build-storybook`, 관련 사용자 흐름의 `pnpm test:e2e`(prod)와 `pnpm test:e2e:dev`(dev) |
| 리팩터링              | 동작을 바꾸지 않는다. 변경 전후 같은 테스트가 통과함을 확인하고, 보호 테스트가 없으면 먼저 추가한다.                                                               | 기능과 같음                                                                                                                                                                                     |
| 문서만의 변경         | 실행 동작 TDD를 억지로 만들지 않는다. 인수 조건마다 반영 위치를 대응표로 확인한다.                                                                                 | 상대 링크·앵커가 실제 대상과 맞는지, `pnpm format:check`, 시작 지침의 참조 확인                                                                                                                 |
| 설정·템플릿 변경      | 영향을 받는 도구가 그 설정을 실제로 읽는지 확인한다(예: 템플릿 frontmatter의 YAML 파싱, 설정 변경 후 해당 명령 실행).                                              | 해당 도구의 검사와 `pnpm format:check`, 빌드·lint 설정이면 영향받는 전체 검사                                                                                                                   |
| 의존성 추가·변경·패치 | 필요성 근거를 남기고 `pnpm-lock.yaml`을 함께 갱신한다. 패치는 `pnpm patch`로만 만든다.                                                                             | 기능의 전체 검사, `docs/decisions.md` 기록                                                                                                                                                      |

- Next 빌드, `next start`, prod E2E는 같은 `.next`를 쓰므로 동시에 실행하지 않는다([빌드 정지 가이드](build-hang-guide.md)).
- 합성 데이터 검증을 실제 임상 검증으로 표현하지 않는다.

## 5. 결과 보고 형식 (Claude → Codex)

```markdown
- 이슈·브랜치: #번호 / <브랜치>
- 시나리오와 인수 조건: 정상 / 경계 / 실패
- Red 증거: 실패 테스트와 실패 이유(로그 경로)
- 변경 내용: 파일별 요약
- 검사 결과: 명령 · 결과(통과 수) · 로그 경로. 미실행은 사유와 함께
- 미검증 항목: 확인하지 못한 환경·데이터·브라우저
- 결정 필요 사항: 권장안 · 대안 · 영향
```

"완료"는 4절의 필수 검사를 모두 통과했다는 뜻으로만 쓴다. Claude의 완료 보고는 감독 Codex에 대한 검수 요청이며, 리뷰 승인이나 병합 허가가 아니다.

## 6. Codex 사전 검수 (PR 오픈 전)

감독 Codex가 PR을 열기 전에 한다. PR 오픈 후의 Codex 리뷰어 리뷰([7절](#7-pr-리뷰와-병합-허가))와는 별개이며, 리뷰어 리뷰가 있다고 생략하지 않는다.

- diff 전체를 직접 읽고 구조(FSD 계층·공개 진입점), 타입, hook, 컴포넌트·Stories, 테스트가 인수 조건을 실제로 검증하는지 확인한다.
- Claude가 보고한 검사 결과를 그대로 옮기지 않고 필요한 검사를 직접 실행한다. 결함을 찾으면 가능한 한 회귀 테스트(`*.review.test.*`)로 먼저 재현한 뒤 수정 지시한다.
- 미해결 지적이 남아 있으면 PR을 review-ready로 열지 않는다.

## 7. PR 리뷰와 병합 허가

리뷰 결과와 병합 허가는 서로 다른 단계다. 리뷰어의 "결함 없음" 판정과 그 PR 댓글은 리뷰 결과일 뿐이며, `main` 병합은 7.3의 사용자 직접 병합이나 명시적 병합 요청으로만 허가된다. 사용자가 명시적으로 병합을 요청하기 전에는 어떤 경우에도 병합하지 않는다.

### 7.1 Codex 리뷰어

- PR이 열리면 감독 Codex가 별도 Herdr 패널에 Codex 리뷰어를 만든다.
- 리뷰어는 `review-agent` 스킬(`/Users/jinyu/.codex/skills/.system/review-agent/SKILL.md`)을 실제로 읽고 따른다. 브랜치 끝이 아니라 실제로 병합될 전체 merge diff(`git merge-base` 기준)를 독립 리뷰한다.
- 리뷰어는 파일을 수정하지 않고, 커밋·푸시·리뷰 댓글 게시·병합을 하지 않는다. 지적은 감독 Codex와 Claude에 전달한다.
- 지적이 수정되어 head가 바뀌면 리뷰어가 새 head를 다시 리뷰한다. 이전 head에 대한 판정은 새 head에 적용하지 않는다.

### 7.2 리뷰 결과 게시 (확정된 임시 방식)

- 리뷰어는 `review-agent` 스킬대로 읽기 전용으로만 리뷰한다. 파일 수정, 커밋, 푸시, 리뷰 댓글 게시, 병합을 하지 않고 결과를 감독 Codex에 보고한다.
- 감독 Codex가 같은 계정(`jinyu74`)으로 리뷰 결과를 PR 댓글에 게시한다. 댓글에는 판정, 지적, 리뷰어가 확인한 검증, 리뷰한 head SHA를 담는다([7.5](#75-기록)).
- 이 댓글은 **정식 GitHub Approve review가 아니다.** 댓글 본문에도 그 사실을 적는다.
- GitHub는 PR 작성자 계정이 자기 PR을 Approve하는 것을 막는다. 정식 Approve review는 별도 인증 주체(다른 계정 또는 GitHub App)를 사용자가 정하기 전까지 보류한다. 이 보류는 현재 작업을 막지 않는다.

### 7.3 병합 허가

- `main` 병합은 다음 두 경우에만 한다.
  1. 사용자가 직접 병합한다.
  2. 사용자가 **해당 PR·head에 대해** 명시적으로 병합을 요청하고, 감독 Codex가 병합한다.
- 감독 Codex가 사용자에게 현재 PR 번호와 head SHA를 제시하고 사용자가 그 대상의 병합을 요청하면, 둘을 연결해 기록한다. 사용자가 번호나 SHA를 직접 입력할 필요는 없다.
- 사용자가 병합을 요청한 뒤 head가 바뀌면 리뷰어가 새 head를 다시 리뷰하고, 사용자에게 병합을 다시 요청받는다.
- auto-merge는 켜지 않는다. PR은 병합될 때까지 열린 상태로 둔다.

### 7.4 병합 허가로 보지 않는 것

- 리뷰어의 "결함 없음" 판정, 감독 Codex가 게시한 리뷰 결과 댓글, (도입되면) 정식 Approve review
- 대화 중 기술 방향에 대한 일반적인 동의
- 사용자의 검토 의견이나 "확인했다", "좋다" 같은 검토 승인
- Claude의 완료 보고나 감독 Codex의 사전 검수 통과
- 어느 PR·head에 대한 요청인지 연결할 수 없는 병합 요청

### 7.5 기록

감독 Codex가 같은 계정으로 PR 댓글에 리뷰 기록과 병합 요청 기록을 **따로** 남긴다.

```markdown
리뷰 기록

이 댓글은 정식 GitHub Approve review가 아니며 병합 허가도 아니다.

- 리뷰어 판정: 결함 없음 / 지적 N건
- 지적: 파일:줄 · 내용 · 처리(없으면 "없음")
- 검증: 리뷰어가 확인한 검사·근거
- PR: #번호
- 리뷰한 head SHA: <40자 SHA>
```

```markdown
병합 요청 기록

- 요청 출처: 대화(일시, 감독 Codex가 제시한 PR·head에 대한 요청) 또는 PR 댓글 링크
- PR: #번호
- 병합 요청 대상 head SHA: <40자 SHA>
```

### 병합 조건

사용자가 직접 병합하지 않는 경우, 다음을 모두 만족할 때만 감독 Codex가 병합한다.

1. 병합 요청 기록이 있고, 그 head SHA가 PR의 현재 head SHA와 같다.
2. 리뷰어가 현재 head를 리뷰했고 미해결 지적이 없다.
3. 필수 검사 중 실패하거나 미실행인 항목이 없다.
4. 미해결 사전 검수 지적이나 사용자 질문이 없다.
5. PR이 최신 `main`과 충돌하지 않는다. 충돌을 해결하면 head가 바뀌므로 다시 리뷰하고 병합 요청을 다시 받는다.

## 8. 결정 기준

### 사용자에게 질문하는 결정

다음은 권장안·대안·영향을 함께 질문하고, 그 결정에 의존하는 작업만 기다린다.

- 비용이 드는 결정(유료 서비스, 사용량 크레딧, 요금제)
- 외부 서비스 생성·연결
- 배포
- 인증·권한 모델
- 원본 데이터의 보관·전송·삭제
- 큰 범위 변경(이슈 범위 확대, 아키텍처·주요 의존성 교체, 기존 사용자 결정 변경)

이미 사용자가 승인한 결정과 같은 범위의 권한은 다시 묻지 않는다. 예: 확정된 리뷰·병합 허가 방식, 허용된 도구·명령, 이미 정한 기본값. 새 비용, 새 서비스, 범위 변경이 생길 때만 새로 질문한다. 이전 승인이 지금 작업에도 해당하는지 불확실하면 그 부분만 질문한다.

### 자율로 판단하는 일

이슈 범위 안의 일상 구현은 묻지 않고 진행한다. 예: 내부 함수·컴포넌트 구조, 테스트 구성, 이름, 기존 규칙 안의 라이브러리 사용법, 문구 정리. 판단 근거가 이후에 중요하면 `docs/decisions.md`에 남긴다.

## 9. 금지 사항

- `main`에서 직접 수정·커밋하거나 `main`에 직접 푸시
- 강제 푸시(`--force`, `--force-with-lease` 포함)로 공유 브랜치 이력을 바꾸는 일
- 사용자의 직접 병합이나 해당 PR·head에 대한 명시적 병합 요청 없이 병합하는 일, auto-merge 활성화. PR은 병합될 때까지 열린 상태로 둔다.
- 리뷰 결과 댓글, 일반 동의, 검토 승인, 완료 보고를 병합 허가로 보는 일
- lint 규칙 비활성화, 테스트 약화·삭제, 타입 검사 우회로 검사를 통과시키는 일
- 요청되지 않은 배포, 외부 서비스 생성, 실제 환자 데이터 전송

## 10. 문서 규칙과 서버 강제의 구분

- 이 문서의 금지 사항과 병합 조건은 **에이전트와 사용자가 지키는 문서 규칙**이다. GitHub가 서버에서 막아 주는 것이 아니다.
- 이슈 #1 작업에서는 원격 저장소 설정(branch protection, 필수 검사, 필수 review, auto-merge 등)을 **변경하지 않았다**. 현재 원격 설정을 조회해 확인한 것은 아니므로, 이 문서는 서버 쪽 기술 강제를 **보장하지 않는다**.
- 서버가 막지 않는 동작(`main` 직접 푸시, 병합 요청 없는 병합 등)이 있더라도, 그것이 허용된다는 뜻이 아니다.
- 서버 강제 설정을 도입하는 일은 권한 모델 변경이므로 [8절](#8-결정-기준)에 따라 사용자 결정 후 별도 이슈로 진행한다. 도입한 뒤에는 이 절을 실제 설정 내용으로 갱신한다.
