## 확정된 사용자 결정

- 로컬 Supabase로 개발·테스트한 후 클라우드를 연결한다. 이번 작업에서 클라우드 프로젝트를 생성하거나 원격 DB를 변경하지 않는다.
- 관리자가 생성한 계정만 이메일·비밀번호로 로그인한다. 공개 회원가입·소셜 로그인은 제공하지 않는다. Auth 서버 설정에서도 공개 가입을 막는다.
- DICOM 원본은 이번에도 DB·Supabase Storage·정적 public 폴더로 보내지 않는다.
- PR 이후 리뷰 결과는 같은 GitHub 계정의 댓글로 기록하며, main은 사용자가 직접 병합하거나 명시적으로 요청할 때만 병합한다.

## 목표와 범위

로그인/로그아웃, Next.js 서버 세션·쿠키 검증, 검사 목록·뷰어의 인증 접근 제어, 사용자별 브라우저 저장소 분리, 로컬 계정 준비 및 자동 테스트 환경을 구현한다.

현재 영상·결과는 IndexedDB다. 로그인만 붙이고 기존 전역 저장소를 그대로 공유하면 다른 계정에 기존 자료가 노출되므로 사용자별 저장소 경계를 함께 만든다. 기존 익명 저장소를 임의 삭제하거나 로그인한 계정에 자동 귀속하지 않는다. 기존 자료는 보존하고 새 환경에서 재가져오기/기존 JSON 복원 안내를 제공한다. 서버 영상 저장과 메타데이터·결과 DB 전환은 다음 이슈다.

## 시작 전 확인

- `AGENTS.md`, `CLAUDE.md`, `docs/development-workflow.md`, Supabase·React·shadcn 관련 스킬을 따른다.
- 설치된 Next 문서의 authentication, server/client boundary, cookies, proxy, Server Actions, Route Handlers를 읽는다.
- 공식 Supabase 문서와 호환되는 `@supabase/ssr`, `@supabase/supabase-js`, CLI 버전을 확인하고 고정한다. 도구 버전은 mise, 패키지·스크립트는 pnpm만 사용한다.
- Docker 엔진은 현재 실행 중이다. 다른 컨테이너·프로젝트·볼륨을 삭제/초기화하지 않고 전용 로컬 스택을 구성한다. 로컬 CLI의 `--help`를 먼저 읽는다.
- 비용·배포·클라우드 연결·실제 환자 파일 전송은 이번 승인 범위 밖이다. 비밀키·계정 비밀번호·토큰을 로그/PR/커밋에 남기지 않는다.

## 시나리오와 인수 조건 — 구현 전 Red 확인

1. 비로그인 상태에서 `/`, `/studies/{uid}`를 직접 요청하면 보호된 화면/정보를 렌더링하지 않고 로그인으로 이동한다.
2. 관리자가 생성한 로컬 계정의 정상 로그인·새로고침·안전한 내부 경로 복귀·로그아웃이 동작한다. 잘못된 비밀번호와 서비스 오류를 성공으로 표시하지 않는다.
3. 누락·위조·만료 쿠키를 서버에서 검증한다. `getSession`의 user 객체만 신뢰하지 않는다. 토큰 갱신 쿠키가 요청/응답에 보존되며 사용자별 인증 응답을 공유 캐시하지 않는다.
4. 공개 가입 UI가 없고 직접 Auth signup API 요청도 거부된다. 로그인 복귀 경로의 외부 URL·프로토콜 상대 URL·비정상 인코딩 등을 거부한다.
5. 로그아웃 후 직접 URL·뒤로 가기·다른 탭에서 보호 화면과 이전 사용자의 결과가 계속 노출되지 않는다. 클라이언트 인증 상태와 서버 검증 경계를 구분한다.
6. 사용자 A가 가져온 원본·측정·메모는 같은 브라우저의 사용자 B 목록/뷰어/직접 UID 접근에 나타나지 않는다. A 재로그인 시 A 자료는 복원된다. 늦은 비동기 저장이 B 저장소에 쓰이지 않는다.
7. 기존 익명 IndexedDB는 자동 삭제/계정 귀속하지 않는다. 이전 자료와 새 계정 저장소의 차이 및 재가져오기·JSON 복원 절차를 문서화한다.
8. 설정 누락 시 인증 우회나 가짜 로그인을 제공하지 않고 명확히 실패한다. 로컬 E2E는 테스트 전용 계정을 admin 경로로 준비하고 실제 Auth 로그인·쿠키를 사용한다. 프로덕션에서 테스트 우회가 켜지지 않는다.
9. 기존 합성 DICOM E2E 전체(확대 후 도구 전환 포함), 저장 실패·수명주기·JSON 검증 회귀를 유지한다. 로그인 UI는 shadcn 기반으로 기본·로딩·실패·키보드/a11y Stories를 테스트 우선으로 작성한다.

## 구현 구조

FSD 계층을 지키고 서버 전용 Supabase 클라이언트·세션 조회·서버 액션과 클라이언트 UI·hook을 분리한다. 서비스 비밀키는 로컬 관리/테스트 프로비저닝에서만 사용하고 브라우저 번들에는 넣지 않는다. 라우트는 얇게 조립하고, 메타데이터 DB/RLS나 원본 파일 서버를 미리 구현하지 않는다.
